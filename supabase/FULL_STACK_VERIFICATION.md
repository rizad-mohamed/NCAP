Authentication finalization was excluded; authentication implementation was not changed.

## Lighthouse and frontend performance

Test tooling also received targeted corrections: prove client hydration using the password-visibility control before filling credentials, wait for login navigation readiness, use visible application links where available, and verify the destination and subsequent workflow after Firefox's `NS_BINDING_ABORTED` signal. Unrelated navigation errors still fail. Firefox reloads receive the same destination/readiness checks, long combined CRUD workflows use a 120-second budget, and the concurrency test now waits for the actual issuer lock rather than relying on a three-second delay. The navigation helper handles initially blank pages and excludes new-tab links. Mobile tests select the infographic action explicitly, close its dialog and open workspace navigation before logging out. Learning upload waits allow asynchronous preparation/upload to finish. An independent local-Blob probe demonstrated Windows WebKit `MEDIA_ERR_SRC_NOT_SUPPORTED`; affected video cases report a platform skip instead of claiming successful playback. Lighthouse uses fresh browsers before switching accounts to avoid stale instrumentation interfering with Playwright selectors. These changes neither modify authentication application code nor replace backend calls with mocks.

Two failed runs exposed a cleanup-harness defect: deleting a disposable Awareness resource while its media was still active violated `awareness_media_assets_check1`. Cleanup now retires only that administrator's media before removing resources; it retains ownership and an ignored identifier/digest recovery manifest if record cleanup fails. A rollback-only probe reproduced the constraint failure and confirmed the correction. Both older failed runs were recovered using exact fixture IDs, media-owner prefixes and validated audit rows. No disposable accounts remained afterward, and all 11 non-fixture content/progress digests were unchanged. Browser failure artifacts can contain disposable input values; they remain ignored and must never be committed.

## Security and operational review

The operational review initially found 24 successful cron dispatches per job over 24 hours but **12 retained HTTP 500 responses** reporting `Cleanup deferred`. Real service-role Data API probes returned `42501: permission denied for schema private`: the maintenance role could access the media tables but could not reach PostgREST's existing pre-request guard. Forward migration `202610030007_maintenance_request_permissions.sql` grants only private-schema usage and execution of that guard to the server maintenance role. It changes no account-check logic or client-role permissions. Three PGlite regressions reproduce the original denial, verify unchanged suspended-account/anonymous behavior, and prove unrelated private execution remains denied. After applying all seven migrations, both actual Vault-backed cleanup entry points returned **HTTP 200, zero failures**, anonymous POSTs remained **401**, and all 11 content/progress digests were unchanged. Alert delivery and recovery ownership still require operational verification.

- **Secrets:** no privileged credential match was found in tracked source, reachable Git patches or generated build output. Frontend Supabase public configuration is client-safe; server module import boundaries prevent privileged server code entering the client bundle. This is a scan result, not a claim about unreachable/deleted external copies.
- **Database:** all 30 reviewed application tables had RLS enabled. No reviewed public/private `SECURITY DEFINER` function lacked a configured search path; reviewed module migrations use protected paths. Migration verification confirmed secured RPCs, read-only grants, indexes and constraints. PGlite integration complements actual hosted role checks; it does not emulate every Supabase extension.
- **Authorization / IDOR:** real learner/outsider requests were denied for privileged RPCs, private quiz answers/attempt internals, another learner's progress/certificates and role escalation. Self-demotion safeguards and administrator mutation audit events were exercised. UI visibility is supplemented by server authorization.
- **Storage:** Awareness and Learning buckets are private, restrict MIME types and cap files at 100 MiB / 50 MiB. Hosted tests verify draft isolation, signing/upload/replacement/deletion and invalid media. Existing signed URLs remain usable until expiry after publication changes; new signing is denied. Video URL lifetimes depend on duration, so immediate revocation of an already issued URL is not guaranteed.
- **Content exposure:** published Learning content/blocks are readable through the existing public Data API policies even though the lesson UI requires sign-in. Private progress is owner-scoped. This existing architecture was not changed as an authentication task.
- **Application review:** reviewed rendering, validation, error paths, upload handling, bearer-authenticated mutations, CSV escaping, PDF inputs and server authorization. No confirmed injection/XSS defect was found in these reviewed paths. This is not a penetration-test certification. Existing security headers still need validation on the eventual hosted HTTPS origin.
- **Audit / SOC-oriented findings:** user role/status, content changes and certificate issue/revoke/template changes have audit trails. Announcements lack a dedicated actor/before/after audit history. Denied actions and report exports lack a centralized durable security-event trail. Monitoring, cleanup-failure alert delivery and backup restoration were not operationally verified. No formal SOC certification is claimed.
- **Deleted-account investigation:** account-management audit actor/target foreign keys become null when profiles are deleted, without a retained identity snapshot. This was observed during disposable-account cleanup; it can prevent identifying a deleted actor/target from that table alone. Profile deletion is outside the administrator status-change UI and authentication finalization was excluded, so retention should be addressed in a separate account/audit change.
- **Integrity:** checked lesson/module, quiz/module and certificate/learner parent relationships had zero orphans. Scoped fixture cleanup and baseline digests passed; this does not constitute a complete historical object-to-metadata reconciliation or a backup.

## Reproduction and CI

Run `npm run check`, `npm audit --audit-level=moderate`, `node scripts/security-review.mjs` and the default Playwright suite. Install browser binaries first. For authenticated staging, prepare the disposable video with `node scripts/prepare-qa-video.mjs`, then invoke `node scripts/admin-modules-live.mjs --staging-project=<configured-staging-ref> --project=<profile>` once per profile. This runner requires ignored staging credentials and refuses the wrong project. Set `NCAP_LIGHTHOUSE=1` for the audit run. Never run authenticated destructive fixtures on production.

The GitHub workflow now checks full reachable history/build secrets and dependencies in addition to its existing typecheck, lint, unit/integration, build and five-profile Playwright checks. Final CI run and synchronized Git state are reported with the final commit in the task completion report; this document avoids a self-referential commit SHA.
